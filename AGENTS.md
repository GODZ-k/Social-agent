# AGENTS.md

Guidance for any coding agent working in this monorepo. Each app has its own `AGENTS.md` with the rules for that app; read it before working there.

## Project documents (`docs/`)

All project documents live in `docs/`. Read `docs/MEMORY.md` first in every session (`CLAUDE.md` auto-loads it). Then, as needed: `docs/PRD.md` (what we are building and for whom), `docs/ARCHITECTURE.md` (the system as built), `docs/API_SPEC.md` (the live HTTP API), `docs/SECURITY.md` (threat model, the SSRF and prompt-injection boundaries, secrets), `docs/TASKS.md` (roadmap board: priority, status, progress), `docs/LESSION.md` (lessons learned — add to it when something costs time twice), `docs/DESIGN.md` (the design system; web, landing and `packages/ui` all follow it), `docs/DESIGN_TRACKER.md` (every frontend screen from design to code: ID, route, design link, approval, Stitch, coded; update it with every design, approval or coding step), `docs/HANDOFF.md` (how to pick up the frontend redesign on a new machine or session: owner rules, waves, agent briefs in `docs/handoff/`). Rules live in this file and the per-app `AGENTS.md`. Detailed specs and plans are under `docs/superpowers/`.

## Agent skills

All skills live at the repo root, whichever app uses them (decided 2026-09-22: one place, loaded no matter which folder Claude Code starts in):

- `.agents/skills/<name>` holds the files. `.claude/skills/<name>` is what Claude Code loads. Both trees are committed, so a clone gets the skills either way. Installers are inconsistent about the second tree: most entries are full copies, a few are junctions pointing back at `.agents/skills` (on Windows without admin rights a junction is all you can make: `New-Item -ItemType Junction`). Either works. What does not work is one tree without the other, so after any install or delete, check both — a skill missing from `.claude/skills` never loads, and a copy left there still loads after you delete the original. A junction whose target you deleted goes dangling, and `test -e` reports it absent while it is still listed: `cmd //c dir /A .claude\skills` is the honest view.
- `skills-lock.json` records where each installed one came from. It is incomplete and cannot be fully rebuilt: 15 of the 43 installed skills have no entry, because the installer that added them never wrote one (`brand-scan-firecrawl` is ours and has no upstream at all). Entries are safe to delete, never to invent — a fabricated `computedHash` is worse than a missing record.
- Here now, 43 skills (pruned 2026-09-23, pruned again 2026-10-01 from 65 to 43): `apple-design`, `frontend-design`, `ux-designer` and `figma-interface` (web, landing, ui); `vercel-react-best-practices`, `vercel-composition-patterns` and `web-design-guidelines` (every React component); `transitions-dev` and `transitions-polish` (motion); `shadcn-ui` (reference only — this repo's components come from `packages/ui`, never from shadcn); the Next.js skills (`next-dev-loop` for verifying a change in the running app; `next-cache-components-adoption`, fully adopted 2026-09-30; the cache-components optimizer and the partial-prefetching adoption/optimizer); `drizzle`, `neon-postgres`, `zod-4` and `turborepo` (the data and build layers); the Clerk skills we use (`clerk` router, `clerk-nextjs-patterns`, `clerk-custom-ui`; no orgs, no billing, no webhooks, no CLI, no testing, no react-router or TanStack, per `docs/PRD.md` and the decisions in force); `mastra` (the API's agents); `graft` (the code graph, use it before grep); `firecrawl-build-scrape` and `firecrawl-build-search` (official `/scrape` and `/search` guidance; `searchWeb` in `apps/api/src/scan/firecrawl.ts` is the live caller) and `brand-scan-firecrawl` (ours: how the brand scan uses Firecrawl, verified API facts, the test sites and their expected results); four Stitch skills from `google-labs-code/stitch-skills` (`stitch-upload-to-stitch` is the fallback for sending `design/<feature>` screens to Stitch when the Figma MCP call limit is used up, the owner imports them into Figma by hand; needs `STITCH_API_KEY`, and no Stitch MCP is configured — plus `stitch-manage-design-system`, `stitch-extract-design-md`, `stitch-extract-static-html` and `enhance-prompt`). The nine that generated designs or code *from* Stitch were removed on 2026-10-01: this repo runs the other way, designing in HTML from `packages/ui` and uploading afterwards, and a skill that regenerates `docs/DESIGN.md` is a hazard when that file is the authority for three packages. Also `eraser-diagrams` (the eraser MCP is configured); the `caveman` pack (`caveman` reply style, `caveman-review`, `caveman-stats`, `safe-refactor`, `surgical-patch`, `verify-and-stop`, `investigate-first`, `lean-build`, `migration`); and `code-simplifier`, which lives only in `.claude/skills` and is run over changed code before reporting done.
- Two directories are not skills: `clerk-backend-api` and `mastra-factory` hold only `evals/`, `scripts/` or `references/` and no `SKILL.md`, so nothing loads them. They are failed installs, untracked, and deleting them is not recoverable through git — reinstall or remove them deliberately, and do not count them among the 43.
- Before adding a skill, check that the repo actually uses the feature it covers; a skill for an unused feature costs listing tokens every turn and nothing else. Reinstall with `npx skills add` from the root when the feature arrives.

**Using skills is not optional.** The owner installs a skill because they want it used. Every session and every dispatched agent:

1. Loads `caveman` first and replies in that style for the whole session (code, comments, commits and docs stay normal prose, as the skill says).
2. Loads the skills that match the work before writing anything: the three Vercel skills and `next-dev-loop` for `apps/web`; `mastra` for any Mastra file; `brand-scan-firecrawl` for the scan; the Clerk skills for auth.
3. Runs the `code-simplifier` plugin agent over new or changed code before reporting done.
4. Uses `safe-refactor` for restructures, `surgical-patch` for bug fixes, `verify-and-stop` for verification-only passes, `investigate-first` for unclear failures.

**Installing a skill:** always run `npx skills add ...` from the repo root. Running it inside an app creates a second `.agents/skills` and `skills-lock.json` there, which nothing loads.

## Working in this repo

- **Name a value before you pass it** (owner rule, 2026-09-25): `const context = await contextFor(row, lang); const questions = await writeQuestions(context);`, never `writeQuestions(await contextFor(row, lang))`; `const brandFilter = BrandsRepository.reachable(scope, id); ... .where(brandFilter)`. The name is a plain, generic noun for what the function returns (`brand`, `session`, `questions`, `context`, `brandFilter`), so anyone can tell what the value is without opening the function. Inline is fine for zod schema builders, JSX, trivial built-ins, the parts of one `and(eq(...), isNull(...))`, and `Promise.all([...])`. Never move a call out of an `if`, `?:`, `??` or `&&` branch.

- **Design before frontend code** (owner rule, 2026-09-26). Any frontend work (`apps/web`, `apps/landing`, `packages/ui`) starts with a design of the part being built, never with code:
  1. Build the screens as HTML from the real design system (`docs/DESIGN.md`, `packages/ui` tokens and components) in `design/<feature>/`, following the UI/UX rules (`figma-interface`, `frontend-design`, `apple-design`, `web-design-guidelines`).
  2. Every screen is responsive: design and check it at desktop (1440), tablet (768) and phone (390) widths, with no sideways scrolling.
  3. As soon as a design is built, open it in a visible Playwright browser as one review sheet (every screen at 1440, 768 and 390 side by side) so the owner gets one look.
  4. The owner approves or rejects from that look. Rejected: design it again with the next version label ("v2", "v3" …); nothing goes to Stitch. Approved (owner rule, 2026-09-26: upload only after approval): set its row in `docs/DESIGN_TRACKER.md` to approved, delete the versions that were not approved locally, and hand the Stitch upload of the approved screens to a background subagent so the main agent is never blocked. Uploads go to the one Stitch project `330652592731776730` (https://stitch.withgoogle.com/projects/330652592731776730), each screen confirmed on the canvas. Create a new Stitch project only when truly needed, and ask the owner first. Screens uploaded before this rule that were later replaced are removed from Stitch by the owner by hand (the Stitch API cannot delete a screen). Then start coding.
  5. Coding starts only on the owner's go. Each built page is then reviewed by the owner in the running app (owner rule, 2026-09-27): the owner asks for changes or approves. Mark the page's Code field in `docs/DESIGN_TRACKER.md` as build in review, changes asked, or build approved; a page is done only when the owner approves the built page. Before assuming this step needs the owner (almost every route sits behind Clerk auth): check for `agent-browser` (`agent-browser --version`, the `next-dev-loop` skill) *and* a `CLERK_SECRET_KEY` in `apps/web/.env.local` — if both are present, a throwaway Clerk user plus a sign-in ticket (`web-auth-and-roles` memory has the exact `POST /v1/users` / `POST /v1/sign_in_tokens` recipe; delete the user afterwards, never print its email) gets a real signed-in browser session, so the agent can do this check itself instead of declaring it blocked on the owner. Confirmed present 2026-09-29; don't assume it's missing without checking both.
- Package manager is pnpm 11 with Turborepo. Run app scripts with `pnpm --filter <name> run <script>`.
- pnpm blocks dependency install scripts until each is answered under `allowBuilds` in `pnpm-workspace.yaml`. An unanswered one makes every `pnpm run` fail with `ERR_PNPM_IGNORED_BUILDS`.
- A dependency used by `packages/ui` must be declared there at the same version the apps use, so pnpm links a single copy.
