## 2. Owner rules (these were in the local agent memory; they apply to every session)

- **Reply style:** load the `caveman` skill first and reply in it on the terminal. Code, comments, docs and commits stay normal prose.
- **Never commit, stage or push.** The owner does all git.
- **Design before code:** every frontend change starts as an approved design (AGENTS.md, "Design before frontend code"). Built pages must match the approved design exactly: copy, structure, states, and the layout at 1440, 768 and 390.
- **No shortcuts accepted:** if an agent reports it built something differently from the design ("kept the existing form", "simpler"), send it back at once to match. "No data yet" is not a reason to leave a part out; add mock data instead.
- **Build review:** a page is done only when the owner approves the running page. The tracker Code field reads: not coded, coding, build in review, changes asked, build approved.
- **Waves need the owner's go.** When a wave finishes, report it and ask before starting the next one. Never fill a freed slot with next-wave work.
- **Keep the tracker live:** update `docs/DESIGN_TRACKER.md` section 2 on every agent start, finish and owner decision.
- **Model per task (cost rule):** the goal is the best output at the lowest cost.
  - Opus: planning, hard bugs, cross-cutting work, reviewing agent output, the coordinating session.
  - Sonnet: executing a clear brief (coding approved designs, design builders, doc updates, the simplifier pass).
  - Haiku: mechanical jobs (searches, screenshots, uploads).
  - Set `model` on every agent. Keep briefs lean: only the skills needed, graft or partial reads instead of whole files, no screenshots in coding agents, one code-simplifier pass at the end, and about four agents at a time.
- **Near 90% of the plan limit:** when the owner says so, stop starting agents, stop the running ones, and write each one's state (task, brief, files done, what is left) to tracker section 2. Resume after the refill.
- **Forms:** react-hook-form + zod for every form with fields (`apps/web/AGENTS.md`).
- **Data:** server components read from `lib/api/server.ts`; client components write through Server Actions with `useServerAction`. No React Query.
- **Stitch:** upload only approved screens, only when the owner says so, to project `330652592731776730`.
- **Name a value before you pass it** (root `AGENTS.md`).
- **Clean code** means plain small named functions at one level of abstraction; no class restructuring.
- **Agents are reusable assets:** `packages/agents` never imports app code, because the agents are reused in other client work.
- **Eraser diagrams stay current:** every flow change also updates the diagrams in the single Eraser file "Brand Scan Flow".
- **Testing files** live only in `apps/api/testing` (temp files in `testing/temp`); deleting that folder must not break the app.

## 4b. Making `graft` and `codebase-memory-mcp` work on Windows (2026-09-30)

Section 4a said `graft` will not install on Windows and to use grep instead. It does install, with one hand edit. Both tools are configured as MCP servers in the committed `.claude/settings.json`, so a fresh clone will try to start them and fail until the binaries exist.

- **`codebase-memory-mcp`:** `npm i -g codebase-memory-mcp`. It only ever looked broken because the first `npx` run downloads the package and blows past the 30-second MCP connect timeout. Installed globally, it connects.
- **`graft`:** `npm i -g @nanonets/graft` fails building `tree-sitter-kotlin` through node-gyp, because that is the one grammar graft bundles with no prebuilt binary and node-gyp wants Python plus MSVC. Every other grammar it uses (TS, JS, Python, Go, Java, PHP, R, Swift) ships a real prebuilt. Graft imports all of them at the top of `dist/graph/extract.js`, so one missing binding kills the whole tool over a language this repo does not contain. The fix is to stub that one binding: replace `<npm root -g>/@nanonets/graft/node_modules/tree-sitter-kotlin/bindings/node/index.js` with `module.exports = { name: "kotlin", unavailable: true };` plus a comment saying why, and keep the original beside it as `index.js.orig`. Then run `graft build` from the repo root (807 files indexed here). **Reinstalling or updating graft overwrites the stub**, so redo it after either. Installing Python and MSVC instead is the honest alternative; it was judged not worth several GB of toolchain to compile a Kotlin grammar for a repo with no Kotlin in it.
- **Either server can time out on a cold start while being correctly installed** — both did on 2026-09-30, at the 30-second limit. Retry the session before concluding anything is broken, and remember the `graft` CLI works from the shell whether or not its MCP server connected.

## 5. Known issues to carry

- **A third-party modal counts as “outside” to Radix, and will close the dialog that opened it.** Clerk raises its own re-verification modal whenever something sensitive happens (`useReverification` wraps changing a password and turning two-factor on), portalled to `document.body`. Radix's dismissable layer sees a pointer or focus event outside the account card and closes it — taking down the component that owned Clerk's modal and leaving that modal on screen with nothing behind it. `packages/ui`'s `Modal` therefore forwards `onInteractOutside` and `onEscapeKeyDown`, and `features/account/account-dialog.tsx` uses them to ignore anything matching `[class*='cl-']`. Any other dialog that can raise Clerk UI needs the same two guards. **That is only half of it.** Radix also sets `pointer-events: none` on `document.body` while a dialog is open, and the property inherits, so the foreign modal is drawn but cannot be clicked — `document.elementFromPoint` over its buttons returns whatever of yours sits behind it, and Clerk’s Cancel did nothing at all. `apps/web/app/globals.css` gives Clerk’s portal roots their events back with `body > [class*="cl-"]`; the `body >` part matters, because a name-based selector like `[class*="cl-modal"]` is case-sensitive and misses something like `cl-reverificationModalBackdrop`. **When testing this, drive it with real input**: `agent-browser mouse move/down/up` and `press Escape`. A synthetic `new MouseEvent('pointerdown')` does not satisfy Radix's pointer handling, so the dialog stays open no matter what the guard does and the test passes whether or not the fix works — it did exactly that here before the method was changed.
- **The two-factor wizard is drawn for a page, and is reused inside the account dialog.** `TwoFactorSetupFlow` serves both `/two-factor/setup` (a full auth page, 25rem column, 34px `AuthHeading`) and the dialog's security pane (616px wide). The dialog scales it down locally through `InPane` in `security-tab.tsx` rather than forking the steps, so there is one copy of the wizard. If the steps are restyled, check both surfaces. Three things about it were left alone deliberately, since they predate this work and are the same on the page: the first step offers a choice among one option (`authCapabilities.secondFactors` is just `authenticator_app`), the progress says "of 3" when this Clerk instance has backup codes switched off so there are only two steps, and the steps render an `<h1>` inside a dialog already titled with an `<h2>`.

- **The `proxy.ts` route matcher can be walked around, and only the server-side reads actually stop it.** Audited 2026-09-30 after Clerk deprecated `createRouteMatcher` with the warning that path matching "can diverge from how Next.js routes requests and leave protected resources reachable". It does diverge here, and it is not theoretical: the `config.matcher` skips any path ending in `.css`, `.png`, `.html`, `.js`, `.csv`, `.zip` and the rest, and a dynamic segment happily swallows one — signed out, `/admin/clients` redirects to `/sign-in` with 307 while **`/c/kiln-and-clay.css`, `/c/foo.png` and `/admin/clients/user_priya.html` all return 200**. Nothing leaks: the visible text of those 200s is the single word "Cadence", because every protected page reaches `getViewer()` (through its own call or `lib/api/server.ts`, which scopes every read by viewer) or the `AdminOnly` gate, and that redirect happens inside the stream. So the guard that actually holds is the server-side read, exactly as Clerk argues. Two things follow: a signed-out visitor on a dotted path gets a blank 200 instead of the sign-in page, and the app is safe only because every protected page happens to read the viewer — nothing enforces that, and neither `tsc`, `eslint` nor the build would notice a new page that does not. The public matchers are also over-broad: `/invite(.*)` matches `/invitefoo` (confirmed — it 404s rather than redirecting, so it was treated as public), which silently makes any future `/invite*` route public. Narrowing them to `/invite(/.*)?` is a small no-downside fix that has not been made.
- **Two-factor lives in the account dialog now; `/two-factor/setup` is the forced gate and cannot go away.** Managing and turning on two-factor moved into the dialog on 2026-09-30 and `/two-factor/manage` is deleted. `/two-factor/setup` stays because a redirect cannot land in a modal: `getViewer()` sends an admin without two-factor there, and so do Clerk's own `setup-mfa` session task and the invite flow. That last point also killed a tempting idea — that the page could collapse to admin-only copy and get a static shell. It cannot; clients reach it too, so its role-dependent panel, promise, lede and skip button all stand, and the open question about its shell (the third bullet above) stands with them.
- **Clerk's backup codes are off on this instance, and the setup flow used to mishandle that.** `POST /v1/me/backup_codes` answers 403. Until 2026-09-30 `confirmAuthenticatorApp` verified the TOTP code and minted backup codes inside one `try`, so that 403 was reported as a failure to turn two-factor on — while it was already on and the code already spent. The calls are separate now and a failed mint just yields no codes. If backup codes are wanted, that is a switch in the Clerk dashboard, not a code change; turn it on and the save-codes step appears again on its own.

- **`loading.tsx` guards only its own segment's page, not the routes nested below it.** This is the single fact that explains the whole Partial Prefetching sweep on 2026-09-30, and it is easy to get backwards: `app/admin/(agency)/observability/loading.tsx` does *not* put a boundary around `observability/agents`, `/frontend` or `/server`. Next's own bundled docs say it (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/loading.md`: it wraps `not-found.js`, `page.js` and nested `layout.js` — a nested *page* in a deeper segment is not on that list). The observable rule in this repo was exact across nine routes: every route with its own `loading.tsx` passed the shell check, every route without one failed it, regardless of what an ancestor had. When you add a route under a segment that already has a `loading.tsx`, it inherits nothing — give it its own boundary.
- **In this app, a page's first data read is always a request-time read.** Every getter in `lib/api/server.ts` scopes its result to the viewer by calling `isAdmin()` or `canSee()`, both of which reach `getViewer()` and then Clerk's `currentUser()`. So there is no such thing here as a page that "only reads the mock": `getObsAgents()` is as request-dependent as `cookies()`. That is why the blocking-prerender errors pointed at `AdminLayout` even on pages that never mention the viewer. Assume any `lib/api/server.ts` call needs a boundary above it.
- **Open decision — `/two-factor/setup` has no honest App Shell.** It is the one route left reporting a blocking read after the 2026-09-30 sweep, and it was left alone on purpose rather than papered over. The viewer's role decides four separate things on that page: which `TwoFactorPanel` shows, the `promise` string, the lede, and whether a "Not now" button exists. Wrapping the lot in `<Suspense>` would pass the check with an essentially empty shell, which is the anti-pattern; streaming the pieces separately needs `AuthFrame`'s `promise` prop widened from `string` to `React.ReactNode` and three boundaries on one page, which reads as over-engineering for a page an admin sees once. The third option — one role-independent promise — is a copy change, and copy is the owner's call, not an agent's. Pick one before touching it.
- **The auth pages are for people who are not signed in, and the proxy now enforces that** (owner rule, 2026-09-30). `/sign-in`, `/sign-up`, `/verify`, `/forgot-password`, `/reset-password`, `/two-factor` and `/two-factor/lost-access` redirect a signed-in visitor to `/`. Two deliberate exceptions: `/sso-callback` runs while a session is being created, and `/invite` is how someone already signed in joins a brand they were invited to. `/two-factor/setup` and `/two-factor/manage` are account settings rather than authentication, so they stay reachable — `getViewer` sends admins without two-factor to the first of those, and that redirect would loop if it were blocked. The rule to apply when adding a page: if it exists to *get* someone in, block it once they are in; if it manages an account that already exists, do not. That is also why changing a password lives in the account dialog and no longer links to `/forgot-password`.
- **Google sign-in:** the Clerk future API ignores `signIn.sso()` while an unfinished sign-in is pending, so the sign-in and sign-up hooks reset any unfinished attempt when the page mounts (`lib/auth/clerk/flows.ts`). The pages Google returns to are public in `proxy.ts`.

The original description is kept because the symptom is worth recognising: Reproduced twice from clean browser state (cookies and storage cleared, fresh throwaway user): sign in with the right password, Clerk asks for the emailed code (`signIn.status === "needs_client_trust"`), enter the correct code, click "Verify email" — and the page shows `FlowEnded` ("This step has ended") with only "Back to sign in". - **A grid item's automatic minimum will push a page sideways at 390.** `/account` overflowed (`scrollWidth` 523 against a 390 viewport) even though the long email was already `truncate`d inside a `min-w-0 flex-1` parent: `min-w-0` makes a *flex* item shrink, but the panel is a **grid** item, whose `min-width: auto` let its min-content (507px) size the track and stretch all four panels. Fixed with `grid-cols-[minmax(0,1fr)]` on the grid. Worth checking any other bare `grid gap-*` that can hold a long unbroken string. To find the culprit fast, walk the DOM for `scrollWidth > clientWidth`, then measure each candidate's min-content by cloning it into an off-screen `width: min-content` box.
- **Never run `next build` and `next dev` over the same `.next`.** It leaves the directory in a state that breaks routes in ways that look exactly like code bugs: on 2026-09-30 every `/admin/c/[brandId]/*` sub-route returned "We can't find that page" while the workspace root rendered fine, and earlier the same day Turbopack reported "Reading source code for parsing failed" for routes renamed in an older session. Both cleared by stopping the server, deleting `apps/web/.next`, and starting again — no code changed. If a route 404s or fails to parse right after you have switched between build and dev, clear the cache before you start reading the code.
- **`◐ (Partial Prerender)` in the build's route table does not mean the shell has anything in it.** It only says *a* shell prerendered — often just `<html><body>` and framework markup. To see what is actually in one, read the prerendered HTML under `apps/web/.next/server/app/**.html` and strip the tags. That is how `/sign-in` was found prerendering 4 words while `/forgot-password`, same layout and panel, prerendered 81: the difference was an `await searchParams` at the top of the page. A scratch script that walks those files and prints shell KB and word count per route is worth rewriting whenever you touch rendering.
- **Cache Components is adopted; there are no opt-outs left.** Every `instant = false` and every `// TODO: Cache Components adoption` is gone as of 2026-09-30, so a new blocking read now fails the build rather than being silently deferred. When a page needs `params`, `searchParams`, `cookies()` or the viewer, keep the static chrome in the page body and push the request-dependent part into a `<Suspense>`-wrapped child component in the same file — `app/(auth)/sign-in/page.tsx` and `app/onboarding/manual/page.tsx` are the two clearest examples. Note that `next dev` catches blockers `next build` does not: the build stops at the first failing route, dev validates each route on every load. Sweep the routes in a browser before believing a passing build.
- **Turbopack's cache can serve CSS that is missing a new file's utility classes.** After adding `features/account/*` the dialog rendered unstyled at desktop widths: `sm:w-56`, `sm:flex-col` and `sm:w-44` resolved to nothing while `lg:pl-64` from older files worked, so it read like a Tailwind content-scan problem and is not one. Restarting `next dev` did not clear it. The fix is to stop the server, delete `apps/web/.next`, and start again — deleting it while the server runs is what the `next-dev-loop` skill warns against, and deleting only `.next/dev/types` made it worse (Turbopack then reported "Reading source code for parsing failed" for routes renamed in an earlier session). To tell this apart from a real mistake in one minute, probe the class in the page rather than reading config: create a throwaway element with the class, read its computed style, and compare against a class only older files use.
- **Motion's own transform cancels a Tailwind `-translate-x-1/2` centring.** A dialog centred with `top-1/2 left-1/2 -translate-x-1/2 -translate-y-1/2` lands in the wrong place the moment `motion.div` animates `scale` or `y`, because Motion writes the whole `transform` property and the utility's translate is simply gone (`getComputedStyle(el).transform` reads `none`). Centre with a wrapper instead — `fixed inset-0 grid place-items-center` around the animated card — and leave `transform` to the animation. `packages/ui`'s `Modal` is built that way.

- **The mock DB is stale-shape-prone, on purpose.** `lib/api/mock/db.ts`'s `getDb()` caches `SeedData` on `globalThis.__cadenceMockDb` so it survives `next dev` hot-reloads — deliberate, so in-session mutations (approvals, connections, edits) persist while you iterate. The cost: adding a new top-level field to `SeedData` (`lib/api/mock/seed.ts`) does not retroactively populate the already-in-memory object; existing records read that field as `undefined` until the dev server process is fully restarted (not just hot-reloaded). This has bitten twice this session (a `date-fns` crash on the settings page from two new `Client` fields, then `alertsOf()`'s `db.channels.filter` crashing on ADM-7's new `team`/`channels`/`alerts` fields). If a page that reads a recently-added seed field crashes with "Cannot read properties of undefined", restart the dev server before looking for a code bug — the seed code is usually already correct.
- **A Server Action that mutates before it can fail leaves partial state on a thrown error.** `submitQuestionnaire` (`lib/api/actions.ts`) calls `questionnaire.review(record, sessionId)` — which mutates the record to `status: "approved"` and bumps its review counter — *before* reading `db.research[clientId]!`. When `rescanBrandKit` was changed to `delete db.research[id]` (to force research to restart fresh after a rescan), a later questionnaire approval crashed on that non-null assertion, but only *after* the questionnaire record had already been marked approved — so a failed submit still left the questionnaire partially advanced. Fixed by never deleting the record (`db.research[id] = research.newResearch(client)` instead), but the general lesson stands: in this mock layer, a thrown error inside an action does not roll back mutations already made to shared `getDb()` state earlier in the same action. Order mutations so the part most likely to fail runs first, or don't mutate shared state until every read that could throw has already succeeded.
- **`loading.js`/`loading.tsx` receives no props at all — not even `searchParams`.** Confirmed against Next's own bundled docs (`node_modules/.../next/dist/docs/01-app/03-api-reference/03-file-conventions/loading.md`: "Loading UI components do not accept any parameters"). This mattered for S00a/S00b: `/onboarding` and admin's `brand/new` route can't pick the right skeleton (fresh visit vs. one resuming with `?clientId=`) from a file-based `loading.tsx`. The fix, if a route ever needs a props-aware fallback: move the slow data fetch into a child Server Component, wrap it in an explicit `<Suspense fallback={...}>` inside `page.tsx` itself (which *does* see `searchParams`), and pick the fallback there. See `features/onboarding/onboarding-entry.tsx` and both `app/onboarding/page.tsx` / `app/admin/(brand)/c/[brandId]/brand/new/page.tsx` for the pattern. Keep `notFound()` calls in whichever half (outer or suspended) actually gates that check — it must run before anything that suspends.
- **A file that only re-exports a client component still needs its own `"use client"` directive.** Next.js 16's Turbopack build checks the re-exporting file, not the file it points to. Bit the admin mirror's `error.tsx` (`export { default } from "@/app/c/[brandId]/error"`), which broke every route under `/admin/c/:brandId/...` until a bare `"use client";` was added above the export. `tsc --noEmit` and `eslint` both missed it — only `next build` (or `get_compilation_issues` over `/_next/mcp`) catches it. Worth a proactive `grep -rL "use client" $(grep -rl "^export { default } from" app)` sweep after any route-tree rename.
